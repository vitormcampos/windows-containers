# AGENTS.md

The application uses:

* C# / .NET
* Avalonia UI
* MVVM
* Microsoft.WSL.Containers
* WSL 2
* Visual Studio 2026

The primary UI project is:

```text
WindowsContainers.UI
```

The solution is:

```text
WindowsContainers
```

The solution and UI project already exist.

**Do not recreate the solution or the `WindowsContainers.UI` project.**

# 9. Views

Avalonia Views belong in:

```text
WindowsContainers.UI/Views/
```

Examples:

```text
MainWindow.axaml
ContainersView.axaml
ImagesView.axaml
SettingsView.axaml
```

Views are responsible for:

* Layout
* Controls
* Styles
* Bindings
* Data templates
* Visual states
* User interaction presentation

Views must NOT contain:

* WSL operations
* Container management logic
* Business rules
* Infrastructure access
* Microsoft.WSL.Containers calls

Keep `.axaml.cs` code-behind minimal.

Prefer MVVM bindings and commands.

## View organization

Separate complete navigable screens from reusable visual elements:

```text
WindowsContainers.UI/Views/
├── Pages/
│   ├── DashboardPage.axaml
│   ├── ContainersPage.axaml
│   ├── ImagesPage.axaml
│   └── SettingsPage.axaml
│
└── Components/
    ├── StatusBar.axaml
    └── Settings/
        └── *Section.axaml
```

`Views/Pages` contains screens reached through the main application navigation. `Views/Components` contains reusable controls and visual sections; components must not own page navigation. Keep matching ViewModels organized under `ViewModels/Pages` and `ViewModels/Components` when those groups are created.

## Application settings persistence

SQLite may persist only WindowsContainers-owned preferences and defaults, such as appearance, container defaults, and desired session defaults. Never persist WSL/wslc runtime state, discovered resources, container state, SDK objects, runtime versions, or effective resource values. Runtime information must be queried from the SDK, runtime, or CLI when needed.

PowerShell aliases are application-owned integration preferences. Store their definitions in SQLite, but validate their actual state against both PowerShell profiles on the machine. Cached status must never replace a fresh machine inspection.

# 11. Services

Container infrastructure should initially live under:

```text
WindowsContainers.UI/Services/
```

Use abstractions where they provide real value.

Example:

```text
Services/
│
├── Interfaces/
│   ├── IContainerService.cs
│   ├── IImageService.cs
│   └── IProviderService.cs
│
└── WslProviderService.cs
```

The interface represents application needs.

Example:

```csharp
public interface IContainerService
{
    Task<IReadOnlyList<ContainerInfo>> GetContainersAsync(
        CancellationToken cancellationToken = default);

    Task StartAsync(
        string containerId,
        CancellationToken cancellationToken = default);

    Task StopAsync(
        string containerId,
        CancellationToken cancellationToken = default);

    Task RemoveAsync(
        string containerId,
        CancellationToken cancellationToken = default);
}
```

The implementation:

```text
WslProviderService
```

is responsible for interacting with the native wslc SDK/CLI and mapping its results to application models.

# 12. Microsoft.WSL.Containers Boundary

Treat `Microsoft.WSL.Containers` as infrastructure.

Avoid spreading its types throughout the application.

Prefer:

```text
ViewModel
     ↓
IProviderService
     ↓
WslProviderService
     ↓
wslc SDK / CLI
```

instead of:

```text
ViewModel
     ↓
Microsoft.WSL.Containers
```

Map infrastructure objects to application models where appropriate.

For example:

```text
wslc SDK / CLI
        ↓
WslProviderService
        ↓
ContainerInfo
        ↓
ContainersViewModel
        ↓
ContainersView
```

This keeps the UI testable and reduces coupling to the WSL API.

# 14. MVVM Rules

Follow MVVM consistently.

Preferred flow:

```text
User
 ↓
View
 ↓ command binding
ViewModel
 ↓
Service
 ↓
WSL
```

Results flow back through:

```text
WSL
 ↓
Service
 ↓
ViewModel
 ↓ observable state
View
```

Use commands instead of button click handlers whenever practical.

Prefer:

```xml
<Button
    Content="Start"
    Command="{Binding StartCommand}" />
```

instead of:

```xml
<Button
    Content="Start"
    Click="Start_Click" />
```

unless code-behind is technically justified.

# 15. Async Operations

WSL operations may take time.

Examples:

* Pulling images
* Starting containers
* Stopping containers
* Creating containers
* Removing containers
* Reading logs
* Initializing WSL sessions

Never block the Avalonia UI thread.

Prefer:

```csharp
async Task
```

Avoid:

```csharp
.Result
.Wait()
.GetAwaiter().GetResult()
```

in UI flows.

Use `CancellationToken` for operations that can reasonably be cancelled.

---

# 16. Error Handling

WSL failures must not crash the application.

Represent failure states through the ViewModel.

Useful state may include:

```csharp
IsLoading
HasError
ErrorMessage
```

The application should eventually recognize conditions such as:

```text
WSL not installed
WSL version unsupported
WSL Containers unavailable
Session initialization failed
Image pull failed
Container failed to start
Container failed to stop
```

Do not silently fall back to Docker.

Do not display raw stack traces to normal users.

# 23. Agent Workflow

Before changing code:

1. Inspect the solution.
2. Inspect `WindowsContainers.UI.csproj`.
3. Inspect existing Views and ViewModels.
4. Inspect existing NuGet dependencies.
5. Understand existing conventions.
6. Determine the smallest coherent implementation.

During implementation:

1. Preserve existing architecture.
2. Use MVVM.
3. Keep WSL access behind services.
4. Prefer async APIs.
5. Handle errors.
6. Avoid unnecessary dependencies.
7. Avoid premature abstractions.

dotnet restore

Do NOT:

* Introduce unnecessary NuGet packages.
* Introduce architectural layers without a current use case.
* Create additional projects merely for architectural purity.
* Ignore compiler errors.
* Ignore newly introduced warnings.
* Rewrite working code without a concrete reason.

# 27. Project Goal

WindowsContainers aims to provide a lightweight Windows desktop interface for managing Linux containers using WSL's native container capabilities.

The application should prioritize:

* Simple architecture
* Native .NET integration
* Avalonia MVVM
* Responsive desktop UI
* Testable ViewModels
* Isolated WSL infrastructure
* CLI-reproducible development
* Visual Studio 2026 compatibility

Prefer the simplest implementation that correctly satisfies the current requirement.

The architecture should grow with the application rather than ahead of it.
